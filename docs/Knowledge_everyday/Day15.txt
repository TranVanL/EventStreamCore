5. Design API Abstraction 

About component that use POSIX , design easier 
**Big concern : message queue 
- In Linux , it just a one of type IPC . It build with queue that add priority and tag (message type ) , allow process send and receive message follow type 
Famous with bufferd message queue , send to kernel queue , receive read from queue , message has priority , it can be block when full queue 

- But in QNX , with microkernel and driver , filesystem , network ,.... run on user space . kernel only has sheduler , interrupt handling , IPC 
-> IPC message passing become a heart of system . It was design with method channel and connection 
Server will create channel and client attach to channel by creating connection 
And process sending and receiving is synchronous request/response . 

-> A huge different : Linux MQ is buffered asynchronous queue , QNX is synchronous IPC  request / reply

Despite QNX support POSIX API so pthread , mutex , semaphore , and condition-variable abstraction can be shared . 
However , timer , channels , interrupt expose OS-specific semantics and require dedicated backends.


7. High performance and realtime 
- High performance concentrate on : How fast system usually run 
High throughput , average latency low , p99/p999 latency good , use CPU /cache / memory , handle a lot of event 

- Realtime  : It not about how quick ,low latency is not enoguh ,  it about : 
Meet deadline , predictable response time , scheduling policy , priority task , jitter , upper bound of latency 

-> Upgrade to realtime : Need to control hot path with thread priority , CPU affinity , priority inheritance , monotonic timing , bounded queue , and explicit degradation behavior
